## Runtime knowledge versus story knowledge

The runtime may use a pre-discovered schema for understanding, validation tooling, ancestry and companion resolution. It does not thereby create a story event or schema skill.

The headless adapter accepts an optional Playthings-internal `introductions` argument:

```js
[{ kind: 'schema', state: 'qualified', subjectId: 'example.schema.v1', artifactId: 'workspace::definition' }]
```

This is a **host-qualified projection input / fixture API**, not a new Tiinex schema, native metadata sidecar or current Core/App wire API. The flag itself is not proof. The adapter must have qualified the subject identity, loaded Workspace artifact and historical event first. Ordinary `record.schemaId`, a filename or an embedded catalogue entry cannot produce this binding.

The ledger withholds unknown/conflicting introductions, coalesces identical bindings and hides future disclosure on rewind. A schema reference already declared by an earlier artifact may remain visible in its read-only inspector; that is not a schema-discovery or skill claim. An unbound schema may provide the current presentation skin without being displayed as a historical discovery.

If an explicit introduction restricts an exact spatial resource before its introduction, its geometry is also withheld. An event whose original physical route was unavailable stays reported as physically undepicted; it remains in the truthful semantic shelf. This candidate does not invent retroactive occurrence or a deferred-route success.

## Resolver and rendering are different boundaries

Core selects winners by specificity first, then provider precedence. Actual carried Core/App tests cover dynamic schema declarations and schema-owned providers with no repository assumption. They also cover equally ranked ambiguity and collection-key append/override.

Spatial Props collections preserve the returned resources; at least one exact artifact/schema resource is required for Props capability. Inherited-only collections do not activate it. Props alone never creates a physical surface. The small viewport ornament arrangement draws at most three resolved Props resources and three items per resource; this is a drawing budget, not a new resolver precedence rule. Single-sheet depiction channels refuse a resolved multi-sheet collection rather than silently choose one; collection resolution can succeed while that particular renderer cannot display it.

Resources are a **current skin**, not time-versioned proof of historical pixels. Only qualified source history controls story knowledge. Metadata presence is not successful byte decoding. The renderer does not read alpha/color to infer walls, people, responsibility, work or acceptance.

## Continuity policy

- Root hashing preserves coordinates and now admits appended records up to the current budget, including ordinary prototype-looking identifiers.
- A compatible spatial refresh keeps established locations.
- A growth conflict retains the old valid physical world, with new source history in the shelf and an explicit pending-depiction notice. Root Gate offers a deliberate Rebuild.
- Removed/changed records and changed/withdrawn capability receipts cannot keep stale geometry alive for cosmetic continuity. Digests and resource identities are part of the compatibility receipt.
- A completed observation remains completed when later history is appended; a paused earlier observation does not jump to Latest.

The latest complete plan reserves presentation extent. Reserved blank space and the deterministic layout are not a historical claim about source geography, floor numbering or capacity.
